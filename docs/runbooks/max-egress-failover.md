# Автоматический резерв MAX / Channel M

## Включение и параметры

В приватном `config.local.yaml` объединить со своим существующим конфигом:

```yaml
max:
  egress:
    active: home_ru_proxy
    fallback_policy: auto
    fallback: hetzner_direct
    probe_interval_seconds: 30
    failover_after_seconds: 600
    recovery_stable_seconds: 300
    minimum_residence_seconds: 600
    retry_cooldown_seconds: 600
    connect_timeout_seconds: 60
    drain_timeout_seconds: 30
```

Основной профиль должен быть `http_connect`, резерв — `direct`. URL и credentials
остаются в `.env.secrets`. Default в публичном конфиге — `manual`.
После изменения требуется перезапуск единственного bridge штатным deploy.
Не менять роутерную LAN/Wi-Fi или другие каналы ради этой функции.

## Поведение

Внутренний MAX watchdog вызывает `MaxEgressController`. Каждые 30с выполняются
TCP/CONNECT/TLS-пробы до фактического endpoint из PyMax с его MAX CA trust.
При offline MAX и непрерывном сетевом отказе 600с контроллер проверяет резерв,
дренирует операции, закрывает старый клиент и создаёт новый с прежней сессией.
API, загрузки и uploads переходят вместе. Авторизация по SMS автоматически
не запускается. Auth failures и отдельные ошибки файлов не меняют маршрут.

Готовность подтверждается подключением клиента, не пробой TCP. На подключение
даётся 60с; неудача вызывает откат и cooldown 600с. При неуспешном закрытии
процесс перезапускается, второй клиент не создаётся. Self-heal запускается
только при offline-клиенте и доступном активном маршруте, вне перехода.

На резерве проверяется основной путь; возврат после 300с успешных проверок,
не раньше 600с пребывания на резерве. Резерв разрешён до восстановления,
без максимального срока. Длинный перерыв наблюдения сбрасывает доказанную
непрерывность отказа/восстановления; рестарт сохраняет cooldown и перепроверяет сеть.

Состояния: `primary`, `waiting`, `switching`, `fallback`, `returning`, `rollback`,
`auth_blocked`. Готовность MAX — отдельный признак.
`data/max_egress_controller.json` хранит состояние, номер инцидента, последовательность
и недоставленные системные события. Этот файл входит в штатный backup `data/`.

## Telegram-трассировка

Ops-топик получает начало отказа после двух проверок, ожидание, переход,
подтверждение подключения, обнаружение восстановления, возврат и итог.
Owner DM получает подтверждённый резерв/возврат и ошибки, требующие внимания.
Без ops-топика события направляются владельцу.

Пример: `[MAX watchdog · M-0042 · 3] 28.09 14:10:30 МСК` →
`MAX подключён через VPS. Доставка возобновлена; проверяем Channel M.`
Каждая запись содержит профиль и online/offline. Напоминание на резерве — 4ч.
Задержанные записи сохраняют исходное время. Сетевые пробы не спамят Telegram.

`/status` показывает маршруты, фазу, длительности и следующее действие.
Read-only status API дополнительно отдаёт `max_egress_controller` с безопасными
результатами проверок и deadline. Внешний watchdog не переключает маршруты;
проверяет просрочку, offline, остальные подсистемы и alert outbox независимо.
Сырые исключения, адреса proxy и данные сообщений не включаются в трассировку.

## Проверка и безопасные учения

1. Выполнить полный CI-набор: compileall, оба набора Ruff/mypy, pytest с coverage
   не ниже 75%, Ansible syntax/lint. Новые сценарии — `tests/test_max_failover.py`.
2. Зафиксировать отправленный commit и предыдущую production-версию. Выполнить
   штатный `backup.yml`, проверить архив и SQLite. Развернуть exact commit.
3. Проверить online MAX через основной маршрут, свежесть status API и наблюдателя.
4. Для учения блокировать только TCP bridge-контейнера к Channel M listener.
   Адрес и порт взять из приватного окружения, не записывать в публичный git.
   До блокировки поставить независимый host timer удаления конкретного правила;
   проверить, что таймер активен. Не трогать SSH, Telegram или роутер целиком.
   `scripts/max_egress_drill.py` выполняется root на хосте; правило ставится
   в OUTPUT network namespace только bridge-контейнера. Host INPUT не подходит:
   штатный Channel M firewall timer периодически поднимает ACCEPT выше него.
5. Короткий отказ 300с: маршрут не меняется. Снять правило и подтвердить online.
6. Длинный отказ: держать до подтверждённого перехода (600с плюс время обнаружения
   offline и подключения). Проверить прямой маршрут, Telegram-трассировку,
   очереди и единственный контейнер/клиент. Снять правило, дождаться возврата
   с учётом 300с стабильности и 600с minimum residence.
7. Текст и поддерживаемые медиа проверять в обе стороны только в выделенном
   тестовом диалоге. Если чат/доступ не предоставлен, явно отметить непроведённую
   часть, не подменять её проверкой сокета или mock-тестом.
8. Удалить правило и таймер, проверить основной маршрут и сохранить обезличенный
   отчёт: времена, пороги, результаты, ограничения. При проблеме выполнить откат.

## Откат и ограничения

Поставить `fallback_policy: manual`, `active: home_ru_proxy`, затем штатно
перезапустить bridge. При необходимости развернуть предыдущий сохранённый release.
Приватный state и существующую session.db не заменять пустыми файлами.
Не запускать дополнительный MAX-клиент для диагностики рядом с production.

Failover не гарантирует полное воспроизведение истории простоя. Действуют
существующие retry queues и ограниченное восстановление истории. Отправка с
неопределённым результатом автоматически не повторяется из-за самого переключения.
Изменение внешнего IP может быть отклонено MAX; такой результат показывается
как неудачное подключение/авторизация, а не как успешный резерв.
